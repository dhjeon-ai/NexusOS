# ProjectOS Reporting Style

## Purpose

Keep progress reporting readable for non-developers and stable across sessions.

## Recommended order

1. what changed
2. why it changed
3. how it affects the user
4. what remains

## Reporting rules

- start long explanations with a one-line summary
- define new concepts in one sentence before expanding
- prefer status words such as working, not yet verified, or has risks
- explain the role of files, not only their names
- when blocked, explain why it is blocked before listing technical errors

## Decision prompts

When the user must choose, ask for only one decision at a time and frame the options by goal:

- fastest
- safest
- most scalable
